Arquitectura genérica con patrón Strategy — MLOps Stack

1. Contexto y motivación

El stack original de MLOps estaba fuertemente acoplado a un único caso de uso: clasificación del dataset Iris con RandomForestClassifier. La carga del dataset (load_iris()), los nombres de features/clases, los hiperparámetros del modelo y la forma de la respuesta de /predict estaban hardcodeados y duplicados en cinco servicios distintos (model-trainer, inference-api, drift-detector, retrain_trigger y los cuatro módulos de tests/).

El objetivo del refactor fue introducir una capa de abstracción basada en los patrones Strategy y Registry para que el stack soporte, sin más cambios de código:

  • Distintas fuentes de datos (datasets de sklearn, CSV propios, etc.).
  • Distintas familias de modelo (Random Forest, Logistic/Linear Regression, etc.).
  • Distintos tipos de problema (clasificación, regresión).

El caso Iris/RandomForest se convirtió en el primer "ejemplo" dentro de esta arquitectura genérica — sin cambiar su comportamiento observable (mismas métricas, mismos endpoints, mismos quality gates).

2. Estructura del paquete mlops_common

Se creó un paquete compartido mlops-stack/mlops_common/, importado por los cuatro servicios Python vía un build context común de Docker: 

mlops-stack/
  mlops_common/
    config.py                # ExperimentConfig (dataclasses) <- YAML
    data_sources/
      base.py                 # DataSource (ABC) + DatasetBundle
      sklearn_dataset.py       # SklearnDatasetSource
      csv_source.py            # CsvDataSource
    models/
      base.py                  # ModelStrategy (ABC)
      classification.py         # RandomForest / LogisticRegression
      regression.py             # RandomForest / LinearRegression
    problem_types/
      base.py                  # ProblemType (ABC)
      classification.py         # ClassificationProblem
      regression.py             # RegressionProblem
  configs/
    iris-classifier.yaml      # "ejemplo" Iris (equivalente al setup original)

Un único archivo YAML (apuntado por la variable de entorno MODEL_CONFIG) conecta una fuente de datos, una familia de modelo y un tipo de problema — y ese mismo archivo es usado por model-trainer, inference-api, drift-detector y tests/.

3. Las tres abstracciones (Strategy + Registry)

3.1 Fuente de datos — DataSource / DatasetBundle

Cada fuente de datos concreta sabe cómo obtener X, y y los nombres de features/target, y los expone con una forma uniforme: 

class DatasetBundle:
    X: pd.DataFrame
    y: pd.Series
    feature_names: List[str]
    target_names: Optional[List[str]] = None  # clasificación
    target_name:  Optional[str]       = None  # regresión

class DataSource(ABC):
    def load(self) -> DatasetBundle: ...

DATA_SOURCE_REGISTRY = {
    "sklearn_dataset": SklearnDatasetSource,  # load_iris, load_wine, ...
    "csv":             CsvDataSource,          # CSV propio + target_column
}

SklearnDatasetSource(name="iris") reemplaza los ocho load_iris() directos que existían antes. CsvDataSource lee cualquier CSV bien estructurado: todas las columnas excepto target_column son features, y decide automáticamente si el target es de clasificación o regresión según su tipo y cardinalidad.

3.2 Familia de modelo — ModelStrategy

class ModelStrategy(ABC):
    def build(self, params: dict): ...        # estimador sklearn sin entrenar
    def fit(self, model, X, y): ...
    def predict(self, model, X): ...
    def predict_proba(self, model, X): ...     # solo clasificación
    def cv_score(self, model, X, y, cv, scoring): ...

MODEL_REGISTRY = {
    "random_forest_classifier": RandomForestClassifierStrategy,
    "logistic_regression":      LogisticRegressionStrategy,
    "random_forest_regressor":  RandomForestRegressorStrategy,
    "linear_regression":        LinearRegressionStrategy,
}

3.3 Tipo de problema — ProblemType

class ProblemType(ABC):
    name: str
    primary_metric: str   # "mayor es mejor" siempre

    def compute_metrics(self, y_true, y_pred, y_proba=None) -> dict: ...
    def quality_gate(self, metrics, gates_cfg) -> (bool, list[str]): ...
    def build_predictions(self, y_pred, y_proba, bundle) -> list[dict]: ...
    def concept_drift(self, reference, current, p_value_thr) -> (bool, dict): ...

PROBLEM_TYPE_REGISTRY = {
    "classification": ClassificationProblem(),  # accuracy/precision/recall/f1, chi2
    "regression":     RegressionProblem(),       # mae/rmse/r2, KS sobre predicciones
}
ClassificationProblemRegressionProblem
primary_metric accuracy r2
compute_metrics accuracy, precision, recall, f1 mae, rmse, r2
build_predictions [{class_id, class_name, probability}] [{value}]
concept_drift Chi² sobre distribución de clases predichas KS test sobre valores predichos

Elegir primary_metric "mayor-es-mejor" en ambos casos evita lógica de dirección (¿subió o bajó es mejor?) en retrain_trigger.py: la decisión de promoción es siempre challenger_metric >= champion_metric + MIN_DELTA.

3.4 Configuración — ExperimentConfig (YAML)

El archivo configs/iris-classifier.yaml describe el caso de uso completo y reemplaza los hiperparámetros/umbrales que antes estaban duplicados en train.py y retrain_trigger.py: 

name: iris-classifier
problem_type: classification

data_source:
  type: sklearn_dataset
  name: iris

model:
  family: random_forest_classifier
  params:
    n_estimators: 200
    max_depth: 8
    min_samples_split: 4
    min_samples_leaf: 2
    class_weight: balanced
    random_state: 42

training:
  test_size: 0.25
  stratify: true
  cv_folds: 5

mlflow:
  experiment_name: iris-production
  registered_model_name: iris-classifier

quality_gates:
  min_accuracy: 0.90
  min_f1: 0.90
  min_per_class_recall: 0.80
  max_cv_std: 0.05

drift:
  data_drift_method: ks
  data_drift_p_value: 0.05
  concept_drift_p_value: 0.05
  performance:
    enabled: true
    consecutive_windows: 2

retrain:
  challenger_min_improvement: 0.0

La ruta del config se inyecta vía la variable de entorno MODEL_CONFIG (default /app/configs/iris-classifier.yaml), configurada por servicio en docker-compose.yml.

4. El caso Iris como "ejemplo" dentro de la arquitectura

Con estas tres abstracciones, cada servicio queda así: 

cfg      = load_config()                         # MODEL_CONFIG -> ExperimentConfig
bundle   = get_data_source(cfg.data_source).load()   # DatasetBundle
strategy = get_model_strategy(cfg.model.family)       # ModelStrategy
problem  = get_problem_type(cfg.problem_type)          # ProblemType

model-trainer/train.py además registra tags de esquema en el run de MLFlow (problem_type, model_family, feature_names, target_names/target_name, config_name). Esto permite que inference-api y drift-detector sean agnósticos del dataset: leen el esquema desde el run de MLFlow en lugar de tenerlo hardcodeado, con fallback a MODEL_CONFIG para modelos legacy.

5. Flujo Drift → Retrain → Promote (ya genérico)

drift-detector (KS sobre features, concept drift vía problem.concept_drift,
                performance drift vía problem.compute_metrics)
  → tras N ventanas consecutivas con drift:
     retrain_trigger.trigger()
       → bundle  = get_data_source(cfg.data_source).load()
       → strategy = get_model_strategy(cfg.model.family)
       → problem  = get_problem_type(cfg.problem_type)
       → entrena challenger, mide problem.compute_metrics()
       → promueve si challenger[primary_metric] >= champion[primary_metric] + MIN_DELTA
       → POST inference-api:8000/reload
Verificación end-to-end realizada sobre la rama refactor-generalization:
  • model-trainer produjo las mismas métricas que antes del refactor (accuracy=0.9211, f1=0.9209, cv_mean=0.9533) más los nuevos tags de esquema en MLFlow.
  • inference-api: /health, /info, /predict devolvieron el contrato esperado.
  • test-runner: 71/71 tests pasaron (data, model, api, performance-drift) → PROMOTION ALLOWED.
  • drift-detector: ciclo completo de detección de drift, entrenamiento de challenger, promoción y /reload ejecutado exitosamente (v11 → v12, accuracy 0.9211 → 0.9474).

6. Cómo agregar un segundo ejemplo: regresión sobre un CSV ad-hoc

Gracias a CsvDataSource y RegressionProblem, agregar un caso de regresión sobre un CSV propio no requiere cambios de código, solo un nuevo archivo de configuración y los datos:

6.1 Ubicar el CSV

Como es un dataset ad-hoc (no versionado dentro de la imagen), se monta como volumen de solo lectura: 

# docker-compose.yml
volumes:
  - ./data:/app/data:ro

6.2 Crear configs/mi-regresor.yaml

name: mi-regresor
problem_type: regression

data_source:
  type: csv
  path: /app/data/mi_dataset.csv
  target_column: precio        # columna numérica continua

  params:
    n_estimators: 200
    max_depth: 8
    random_state: 42

  test_size: 0.25
  stratify: false               # no aplica a target continuo
  cv_folds: 5

  experiment_name: mi-regresor-production
  registered_model_name: mi-regresor

  min_r2: 0.70
  max_rmse: 5.0

drift:
  data_drift_method: ks
  data_drift_p_value: 0.05
  concept_drift_p_value: 0.05   # KS sobre predicciones (RegressionProblem)
  performance:
    enabled: true
    consecutive_windows: 2

6.3 Apuntar MODEL_CONFIG al nuevo config

Reutilizando las mismas imágenes Docker, basta con otro set de servicios (o cambiar las variables de entorno del set existente): 

environment:
  MODEL_CONFIG: /app/configs/mi-regresor.yaml
  MODEL_NAME:   mi-regresor

7. Algoritmos "ad-hoc" no disponibles en sklearn

Las secciones anteriores reutilizan familias ya registradas en MODEL_REGISTRY (Random Forest, Logistic/Linear Regression). El patrón Strategy permite incorporar cualquier algoritmo — de una librería externa o 100% escrito a mano — siempre que se exprese como una nueva subclase de ModelStrategy registrada bajo una nueva clave. El resto del stack (train.py, inference-api, drift-detector, retrain_trigger) no cambia: solo consume get_model_strategy(cfg.model.family).

Se ilustran dos casos: (A) un regresor de una librería externa no usada hoy en el stack (XGBoost), y (B) un clasificador escrito completamente desde cero (sin ninguna librería de ML).

7.A — Regresor de una librería externa: XGBRegressor

xgboost no está instalado en las imágenes actuales, pero XGBRegressor ya implementa la API de sklearn (fit/predict/get_params/set_params), por lo que la estrategia es casi un envoltorio directo: 

# mlops_common/models/regression.py
from xgboost import XGBRegressor

class XGBoostRegressorStrategy(ModelStrategy):
    def build(self, params):
        return XGBRegressor(**params)
    # fit / predict / cv_score: se heredan de ModelStrategy sin cambios,
    # porque XGBRegressor ya es compatible con cross_val_score.
    # predict_proba: no aplica a regresión (NotImplementedError por defecto, correcto)

Registrar la nueva familia:

# mlops_common/models/__init__.py
MODEL_REGISTRY = {
    ...,
    "xgboost_regressor": XGBoostRegressorStrategy,
}

Agregar la dependencia en los Dockerfiles que entrenan/evalúan el modelo (model-trainer, drift-detector, tests):

# Dockerfile — capa de dependencias científicas
RUN pip install --no-cache-dir --timeout=120 --retries=5 \
    numpy==1.26.4 pandas==2.2.2 scipy==1.13.0 scikit-learn==1.4.2 \
    pyyaml==6.0.1 xgboost==2.0.3

Y referenciarla desde el YAML del experimento:

# configs/mi-regresor.yaml
model:
  family: xgboost_regressor
  params:
    n_estimators: 300
    max_depth: 4
    learning_rate: 0.05
    random_state: 42

7.B — Clasificador 100% custom (sin librerías de ML)

Para un algoritmo que no existe en ninguna librería, se implementa una clase que siga la API de estimador de sklearn (fit/predict/predict_proba) heredando de BaseEstimator + ClassifierMixin. Esa herencia es lo que le da get_params/set_params "gratis", necesarios para que cross_val_score (usado por ModelStrategy.cv_score) y mlflow.sklearn.log_model funcionen sin más cambios.

Ejemplo: un "clasificador de centroide ponderado" — calcula el centroide de cada clase en fit, y en predict_proba convierte las distancias a los centroides en probabilidades vía softmax. No existe como tal en sklearn (que solo ofrece NearestCentroid sin probabilidades). 

# mlops_common/models/custom_centroid.py
import numpy as np
from sklearn.base import BaseEstimator, ClassifierMixin

class WeightedCentroidClassifier(BaseEstimator, ClassifierMixin):
    """Predice por centroide mas cercano; probabilidad = softmax(-distancia)."""

    def __init__(self, temperature: float = 1.0):
        self.temperature = temperature

    def fit(self, X, y):
        X = np.asarray(X)
        self.classes_ = np.unique(y)
        self.centroids_ = np.array(
            [X[np.asarray(y) == c].mean(axis=0) for c in self.classes_]
        )
        return self

    def predict(self, X):
        return self.classes_[self._distances(X).argmin(axis=1)]

    def predict_proba(self, X):
        logits = -self._distances(X) / self.temperature
        exp = np.exp(logits - logits.max(axis=1, keepdims=True))
        return exp / exp.sum(axis=1, keepdims=True)

    def _distances(self, X):
        X = np.asarray(X)
        return np.linalg.norm(
            X[:, None, :] - self.centroids_[None, :, :], axis=2
        )

La estrategia y el registro siguen el mismo patrón que los demás:

# mlops_common/models/classification.py
from .custom_centroid import WeightedCentroidClassifier

class WeightedCentroidStrategy(ModelStrategy):
    def build(self, params):
        return WeightedCentroidClassifier(**params)

    def predict_proba(self, model, X):
        return model.predict_proba(X)

    @property
    def supports_proba(self) -> bool:
        return True

# mlops_common/models/__init__.py
MODEL_REGISTRY = {
    ...,
    "weighted_centroid": WeightedCentroidStrategy,
}

# configs/iris-centroide.yaml (mismo dataset Iris, algoritmo distinto)
problem_type: classification
model:
  family: weighted_centroid
  params:
    temperature: 1.0

Si el algoritmo no sigue la API de sklearn en absoluto (p. ej. un modelo en PyTorch con su propio ciclo de entrenamiento), la solución es la misma a nivel de arquitectura pero la subclase de ModelStrategy debe sobrescribir fit, predict y cv_score (en vez de heredar los defaults) para adaptar esas llamadas al ciclo de entrenamiento propio del framework — el resto del stack sigue sin cambios porque solo interactúa con ModelStrategy, nunca con la librería subyacente directamente.
