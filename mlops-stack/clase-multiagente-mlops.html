Parte 02

Marco Conceptual

El diseño multi-agente que vamos a estudiar no emerge del vacío: está fundamentado en tres conceptualizaciones de MLOps que el paper identifica como centrales.

Definición 1

MLOps-as-Pipeline-Automation

MLOps como la práctica de automatizar las actividades repetitivas del ciclo de vida ML construyendo y gestionando pipelines automatizados. Los agentes son la realización concreta de esta automatización: cada agente automatiza un dominio específico del pipeline (entrenamiento, serving, calidad, monitoring).

Eken et al. §3.1.3 — 34 estudios la identifican como definición primaria
Definición 2

MLOps-as-Culture + Team Structure

Desarrollar y operacionalizar un sistema ML-enabled requiere colaboración entre muchos roles distintos (business analysts, ML engineers, software engineers). La arquitectura multi-agente modela estructuralmente esta colaboración: cada agente representa un rol, y los mensajes entre agentes modelan la colaboración inter-equipos.

Eken et al. §3.1.4, §4.1 — 18 estudios; clave: "MLOps engineers interact with every role" (PS105)
Definición 3

Microservice Architecture como base del diseño

La Arquitectura de Microservicios (MSA) demuestra alta escalabilidad con servicios independientemente escalables pero interconectados. Nuestro Docker Compose ya implementa este patrón: cada servicio tiene un dominio claro y se comunica por API. Los agentes son la capa de inteligencia que coordina estos microservicios.

Eken et al. §5.3.2 — PS119: MSA recomendada para MLOps platforms; PS111, PS126: modularización vía microservicios
Conexión clave
Docker Compose = Arquitectura de Microservicios. Cada servicio (mlflow, inference-api, drift-detector, nginx) es un microservicio independiente. Los agentes que diseñamos hoy son el siguiente nivel de abstracción: entidades con autonomía que usan estos microservicios para cumplir sus objetivos.
Parte 03

Los Cinco Agentes del Sistema

Cada agente mapea a un rol de Eken et al. Fig. 3 y controla uno o más servicios concretos del stack Docker Compose.

🎛️
Agente Orquestador
MLOE — MLOps Engineer
Servicio Docker: nginx :80 + gestión de GitHub Actions workflows
  • Coordina todos los demás agentes
  • Gestiona pipeline triggers (ci.yml, cd.yml, retrain.yml)
  • Reverse proxy de tráfico de entrada
  • Mantiene estabilidad operacional del sistema
  • Interviene cuando un agente falla o requiere escalación
  • Gestiona dependencias entre servicios
Eken §3.3 — "MLOps engineers are responsible for building automated pipelines, maintaining operational stability of the entire ML system, and facilitating collaboration across roles" (PS106, PS116)
🔬
Agente Data Scientist
DS — Data Scientist
Servicio: model-trainer + MLflow :5001
  • Ejecuta experimentos de entrenamiento
  • Registra métricas, params e hiperparámetros en MLflow
  • Diseña y evalúa modelos candidatos
  • Promueve modelo a Staging en el Registry
  • Itera sobre el modelo si QA detecta problemas
Eken §3.3 — "DS responsible for training, tuning, and evaluating models; ensure trackability of experiments, datasets, and models" (PS121, PS24)
⚙️
Agente ML Engineer
MLE — ML Engineer
Servicio: inference-api :8000 (FastAPI)
  • Carga modelo Production desde MLflow Registry
  • Sirve predicciones vía POST /predict
  • Ejecuta hot-swap vía POST /reload sin downtime
  • Loggea predicciones a predictions.jsonl
  • Monitorea performance en producción
Eken §3.3 — "MLE primary tasks: model optimization, deployment, and monitoring" (PS114, PS154)
🧪
Agente QA Engineer
QAE — Quality Assurance Engineer
Servicio: test-runner
  • Ejecuta tests unitarios sobre el modelo
  • Valida integración con inference-api
  • Verifica SLAs de latencia y accuracy
  • Actúa como puerta de control (gate) antes de producción
  • Notifica al orquestador MLOE si falla
Eken §3.2.8 — "QAE responsible for testing software application and services to ensure product quality" (PS36); Application quality gate
📊
Agente Monitoring
MLOE + DOE — Monitoring / DevOps
Servicio: drift-detector (Evidently AI)
  • Lee predictions.jsonl periódicamente
  • Calcula data drift con PSI / KS test
  • Genera reporte HTML de observabilidad
  • Dispara webhook cuando consecutive ≥ 2
  • El webhook activa retrain.yml en GitHub Actions
Eken §3.2.6 — "training can be triggered when concept drift is detected" (PS102); "leveraging events to detect and respond to model and data issues" §4.3
👁️
Human-in-the-Loop
PM + MLOE — Punto de Intervención Humana
No es un servicio Docker — es un punto deliberado de aprobación manual
  • Revisa métricas de negocio del modelo candidato
  • Valida los drift reports de Evidently
  • Aprueba promoción de Staging → Production
  • Puede rechazar y retornar el ciclo al agente DS
Eken §5.2.5 — "best practice for automation dilemma: automate tedious tasks and incorporate human feedback where possible" (PS110); Human-in-the-loop interventions

Patrón arquitectural
Cada interacción usa un canal diferente: archivos compartidos (JSONL), APIs REST (HTTP), variables de entorno (GitHub Actions), o la UI de MLflow. Esto refleja la naturaleza heterogénea de las integraciones MLOps que el paper identifica como desafío (§5.1.2 Pipeline Fragmentation).
Parte 05

Flujo Completo del Sistema

El ciclo de vida completo, desde un push de código hasta el hot-swap del modelo en producción, pasando por el loop de reentrenamiento automático.

01
Desarrollador hace push a GitHub
Un cambio en el código (nuevo feature, fix, actualización de modelo) es comiteado y pusheado al repositorio. GitHub Actions detecta el evento y dispara ci.yml en el self-hosted runner.
CI/CD trigger GitHub webhook
# .github/workflows/ci.yml
on: [push, pull_request]
jobs:
  build-and-test:
    runs-on: self-hosted
02
QA Gate: Agente QAE valida el stack
El agente QAE ejecuta test-runner sobre el stack actual. Corre tests unitarios e integración. Si algún test falla, el pipeline se detiene y el agente MLOE recibe notificación. Si todos pasan, el pipeline continúa.
QAE activo MLOE recibe resultado
# En ci.yml
- name: Run QA Suite
  run: docker compose run --rm test-runner
03
Deploy: Agente MLOE actualiza el stack
cd.yml actualiza los servicios Docker Compose. El agente MLOE (nginx) empieza a enrutar el nuevo tráfico. El agente MLE (inference-api) carga el modelo actual desde MLflow Registry.
MLOE coordina MLE carga modelo CI/CD ejecuta
04
Producción: Agente MLE sirve predicciones
La inference-api recibe peticiones de usuarios vía nginx. Cada predicción queda registrada en predictions.jsonl en un volumen compartido. Este archivo es la entrada del agente de monitoring.
MLE activo usuarios externos
POST /predict → modelo carga features → retorna clase + probabilidad
→ append a predictions.jsonl (shared volume)
05
Monitoring: Agente MON detecta drift
El drift-detector analiza periódicamente la distribución de features en predictions.jsonl comparada con los datos de referencia (training set). Evidently calcula métricas de drift. Genera reporte HTML visible para el humano.
MON activo HUMAN recibe reporte
# Ciclo de detección
--- Cycle N (drift_phase=True) ---
  Data drift: True  features=['petal length (cm)']
  Consecutive: 2/2 → 🔁 RETRAINING TRIGGERED
06
Trigger automático: webhook → retrain.yml
Cuando drift consecutivo ≥ 2, el agente MON hace un POST al endpoint webhook de GitHub Actions. Esto dispara retrain.yml en el self-hosted runner, que a su vez activa el agente DS.
MON dispara CI/CD recibe
# En drift_detector.py
if consecutive_drift >= threshold:
  requests.post(GITHUB_WEBHOOK_URL, json={"event_type": "retrain"})
07
Reentrenamiento: Agente DS entrena nuevo modelo
retrain.yml ejecuta model-trainer. El agente DS entrena una nueva versión del modelo con datos actualizados, registra el run en MLflow con todas sus métricas, y lo promueve a Staging en el Registry.
DS activo MLOE observa
08
QA Gate del nuevo modelo
El agente QAE valida el nuevo modelo candidato. Si los tests pasan, el resultado va al punto de revisión humana. Si fallan, el ciclo vuelve al agente DS.
QAE gate DS itera si falla
09
Human Approval: revisión y aprobación
Un humano (PM o MLOE) revisa las métricas del nuevo modelo en MLflow, compara con el modelo champion actual, y evalúa el drift report de Evidently. Si aprueba, promueve el modelo a Production en el Registry.
HUMAN decide MLOE Registry
10
Hot-swap: Agente MLE carga el nuevo modelo
El agente MLOE notifica al agente MLE que hay un nuevo modelo en Production. La inference-api ejecuta POST /reload, descarga el nuevo modelo desde MLflow Registry y lo carga en memoria sin reiniciar el servidor ni perder disponibilidad.
MLE actualiza MLOE coordina
# Hot-swap sin downtime
curl -X POST http://localhost:8000/reload
→ {"status": "reloaded", "version": "v3", "stage": "Production"}
Parte 06

Los Cuatro Tipos de Pipeline Triggers

Eken et al. §3.2.6 identifica cuatro tipos de triggers para la automatización de pipelines. Nuestro stack implementa los cuatro.

⚡ Secuencial (Sequential)
Una tarea dispara la siguiente al completarse.
En nuestro stack: model-trainer completa → modelo en Staging → QA gate → Human approval → MLE hot-swap.
PS42 — "executing a task upon the previous task's completion"
🕐 Periódico (Periodical)
Ejecución según un schedule pre-programado.
En nuestro stack: drift-detector analiza predictions.jsonl cada N segundos/minutos de forma continua.
PS25 — "executing according to a pre-scheduled period"
🎯 Event-driven
Un evento en el sistema dispara el siguiente paso.
En nuestro stack: drift consecutivo ≥ 2 → webhook POST → retrain.yml se activa automáticamente en GitHub Actions.
PS102, PS147 — "triggered when concept drift is detected"
📉 Por Degradación (Performance)
Degradación de métricas dispara una acción de recuperación.
En nuestro stack: Evidently detecta degradación estadística en la distribución de features → inicia ciclo de reentrenamiento.
PS140 — "training triggered when model performance is reduced"
Pregunta de diseño
¿Por qué usar consecutive ≥ 2 como threshold para el trigger de reentrenamiento, en lugar de disparar en el primer ciclo con drift? Pista: piensa en falsos positivos y en el costo de un reentrenamiento innecesario.
Parte 07

Human-in-the-Loop: El Dilema de la Automatización

Eken et al. §5.2.5 identifica el "Automation Decision Dilemma" como un desafío central en la adopción de MLOps. No todo debe automatizarse.

Eken §5.2.5 — Automation Decision Dilemma

¿Por qué no automatizar la aprobación de modelos?

Aunque los practicantes tienden a automatizar donde sea posible, el ciclo de vida ML contiene actividades donde el feedback humano es crucial y la automatización total puede crear impactos negativos, especialmente considerando las prácticas de IA responsable. La mejor práctica propuesta es automatizar tareas tediosas e incorporar feedback humano donde sea posible (PS110).

PS110 (Databricks) — Citado explícitamente como best practice para el dilema de automatización

En nuestro sistema, el Human-in-the-Loop tiene responsabilidades que los agentes no pueden asumir solos:

Decisión ¿Por qué requiere humano? Riesgo si se automatiza
Aprobar nuevo modelo a Production Requiere juicio sobre impacto de negocio, no solo métricas técnicas Un modelo técnicamente mejor puede violar requisitos regulatorios o de negocio
Validar drift reports El contexto de negocio puede explicar el drift (campaña estacional, etc.) Reentrenamiento innecesario con datos no representativos del futuro
Decidir rollback Requiere analizar si el problema es del modelo o del sistema/datos Rollback automático puede crear ciclos de degradación en cascada
Punto de discusión
El paper menciona que la ausencia de frameworks de análisis de impacto es una brecha de investigación actual. ¿Cómo diseñarías un criterio objetivo para que el sistema sugiera al humano aprobar o rechazar, sin tomar la decisión final?

Parte 09

Preguntas de Discusión

Estas preguntas conectan el diseño práctico del sistema con las brechas y debates que el paper identifica explícitamente.

1. Eken et al. §5.3.2 señala que la arquitectura monolítica "considerably impacts the scalability of a system" y que MSA "demonstrated high scalability with independently scalable but interconnected services". ¿Cuál de nuestros cinco agentes sería el cuello de botella más crítico bajo alta carga? ¿Cómo lo resolverías?
2. El paper identifica como brecha de investigación que "existing literature does not provide a structured approach" para el automation dilemma (§5.2.5). En nuestro sistema, el Human-in-the-Loop es manual. ¿Qué métricas concretas diseñarías para crear una recomendación automática que asista al humano en la decisión de promover un modelo?
3. Eken et al. §5.2.3 menciona "silent failures caused by data quality issues" como uno de los principales riesgos en pipelines a escala. ¿Qué agente de nuestro sistema es más vulnerable a fallar silenciosamente? ¿Qué mecanismo de alerta agregarías?
4. El paper (PS179) propone "a software agent that pulls and feeds data to containerized ML code" para abstraer la adquisición de datos. En nuestro stack actual, ¿quién cumple ese rol implícitamente? ¿Cómo lo convertirías en un agente explícito con su propio servicio Docker?
Brecha del paper relevante
Eken et al. no identifica en su corpus ningún paper que trate la sostenibilidad ambiental como objetivo primario de MLOps. En un sistema multi-agente real, ¿qué tipo de agente podría monitorear y optimizar el consumo energético del stack (GPU hours, container resources) como primera clase de la arquitectura?
